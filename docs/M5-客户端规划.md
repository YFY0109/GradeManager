## 3. 技术方案（待选）

### 方案 A：Jinja2 + HTMX + Alpine.js（推荐）

- FastAPI 同进程渲染模板，静态资源由 FastAPI/Nginx 提供
- 登录用 **HttpOnly Cookie**（存 JWT），页面请求自动携带
- HTMX 做局部刷新（筛选、保存、分页），Alpine.js 处理表格编辑状态
- 图表用 ECharts（本地静态文件，不依赖 CDN）
- 优点：部署零额外依赖、首屏快、内存低、XSS 风险小（token 不进 JS）
- 缺点：复杂交互不如 SPA，组件需自己写

### 方案 B：Vue 3 + Element Plus + Vite

- 独立 SPA，Nginx 托管 `dist`，API 反代 8000
- 登录用 Bearer token（localStorage）或 Cookie
- 优点：表格/表单组件成熟、交互体验好、易扩展
- 缺点：需要 Node 构建链、发布多一步、包体积与内存更高

### 方案 C：React + Ant Design

与 B 类似，生态偏 React。

> 推荐 A：本项目是内部管理工具，页面以表格/表单为主，服务器内存仅 1.6GB；A 的部署与安全成本最低。

## 4. 认证与会话

| 方案 | 说明 |
|---|---|
| **Cookie 会话（推荐 A）** | 登录成功后设置 `HttpOnly; Secure; SameSite=Lax` Cookie（JWT）；`current_user` 支持 Bearer 或 Cookie；登出清 Cookie；表单 POST 校验 Origin |
| Bearer + localStorage（B/C） | 沿用现有 API；前端拦截 401 跳登录；XSS 风险较高 |

无论哪种，现有 Bearer API 保持兼容（脚本/外部调用不受影响）。

## 9. 风险与边界

| 风险 | 对策 |
|---|---|
| 服务器内存有限 | 方案 A 同进程渲染，避免 Node 常驻；图表按需加载 |
| 9 科数据格式未知 | 先拿到期中表再定列映射与满分 |
| 录入误操作 | 保存前校验 + 审计日志 + 可回改 |
| 移动端录入体验 | 首期不做移动端录入，只做查看 |
| Cookie CSRF | SameSite=Lax + Origin 校验 + 仅同站表单 |
